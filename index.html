Architecture & Security

Event-Sourced Commerce Platform

KotlinSpring BootAxonCQRSOAuth 2.0
The problem
Billing, orders, inventory and subscriptions had grown together in one backend that was getting harder to change safely.
The approach
A modular monolith on an event-sourced core, with each domain as its own module and its own identity and access layer.
Key decisions
Event sourcing over plain CRUD, for a record that can be audited and replayed. Every lookup is scoped to the business making it, so tenant isolation is part of the structure, not a check someone might forget.

Company Operations Platform

KafkaDebeziumRealtimeAI triage
The problem
Sales, support and onboarding were working across scattered tools, with no single view of a customer.

One system of record for leads, orders, support and device onboarding, with AI-assisted triage and work queues that assign themselves.

03 — Design decisions

The calls behind the systems.

Architecture is mostly trade-offs. A few I've made, what lost, and what each choice costs.

Let the device declare its own tools

Context
A server-side agent had to act on hardware it doesn't control, and each device can do different things.
Options
Register every device capability on the server, or have each device announce its tools when a session starts.
Chosen
The device declares its tools, and the server treats that list as untrusted input, scoped to the caller. New hardware features don't need a server release.
The cost
A declared tool is a promise the server can't verify in advance, so validation and timeouts at that boundary matter more than anywhere else.

Event sourcing for commerce

Context
Orders, stock, billing and refunds interact, and every change has to be explainable after the fact.
Options
Plain CRUD tables with an audit log on the side, or events as the source of truth with read models built from them.
Chosen
Event sourcing with CQRS. Writes are checked against the aggregate itself, never against a read copy, so a lagging view can't block a valid write.
The cost
It costs more up front: evolving event schemas and running projections are real work. Worth it for money and stock, not for every module.

Change data capture over dual writes

Context
The CRM and other systems needed every subscription and user change, in real time and without drifting.
Options
Have the backend write to the database and publish to Kafka separately, or publish from a transactional outbox through change data capture.
Chosen
An outbox table captured by Debezium into Kafka. If the transaction commits, the event exists; if it doesn't, nothing leaks.
The cost
Replication slots need watching. A stalled slot quietly grows, so heartbeats and lag alarms went in on day one.
04 — How I work

Design first. Build fast. Own the outcome.

Most of my time goes into the decisions that matter: what to build, how it fits together, and how it stays secure and scales. AI coding tools turn those decisions into working software quickly, and I review and own everything that ships.

  1. 01

    Understand

    Requirements first: who uses it, what happens when it fails, what it costs to run, and what the business actually needs from it.

  2. 02

    Architect

    Settle the design, flows, security model and scaling path before any code, and write it down so anyone can build on it.

  3. 03

    Build fast

    I move from design to working software quickly with AI coding agents like Claude Code. Tests, type checks, an architecture-boundary check and my own review of every change gate what ships.

  4. 04

    Own it in production

    A readiness review before anything risky goes live, alerts I'd want at 3am, and a rollback path for every change. I stay accountable for the outcome, not just the merge.
